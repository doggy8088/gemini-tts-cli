# 語音異常提前結束研究報告

## 結論摘要

本次 live 測試**無法支持**「`gemini-3.1-flash-tts-preview` 對這份輸入有固定 40 秒硬上限」這個說法。相同的 `sample2.txt` 內容，在 Gemini API 與 CLI 實測中都可以產生 **66 到 71 秒**的音訊，而且正常案例的 `finishReason` 會回傳 `STOP`。  

但另一方面，**40.0 秒的異常檔案確實存在**。在與原始指令非常接近的 CLI 重跑測試中，只要隨機選到特定 voice（這次抓到的是 `leda`），就能重現一個**有效但提早結束**的 40 秒 WAV。  

綜合目前證據，最合理的判斷是：

1. 這不是固定的模型 40 秒硬限制。
2. 這比較像是 preview / stream 路徑上的**間歇性早停異常**。
3. 目前 CLI 只要收到了任何音訊資料，就會直接輸出 WAV，**不會把有音訊時的 `finishReason` 當成異常提示給使用者**，因此問題看起來像「成功產生檔案，但講到一半就停」。

## 測試背景

- 測試內容：`examples/sample2.txt`
- 主要模型：`gemini-3.1-flash-tts-preview`
- 主要路徑：`dotnet dnx GeminiTtsCli -- -t "$(cat examples/sample2.txt)"`
- 交叉驗證方式：
  - `countTokens`
  - `generateContent`
  - `streamGenerateContent`
  - CLI fresh run（關閉 cache）

## 主要證據

### 1. Prompt 根本沒有接近官方 token 上限

Gemini `countTokens` 的 live 回應顯示，這份 prompt 只有 **297 tokens**。  
而官方模型文件列出的限制是：

- input token limit：**8,192**
- output token limit：**16,384**

這表示先前「因為打到官方 token 上限，所以固定 40 秒被截斷」的推論，**不成立**。

## 2. 同一份內容可以穩定超過 40 秒

固定使用 `Zephyr` voice 的 live 測試結果如下：

| 測試方式 | 結果 |
| --- | --- |
| `generateContent` | 68.04 秒，`finishReason=STOP` |
| `streamGenerateContent` | 66.28 秒，`finishReason=STOP` |
| CLI fresh run | 71.12 秒，尾端接近靜音，屬自然收尾 |

這是最直接的反證：**同一份內容明確可以超過 40 秒**。

### 3. 40 秒檔案是真實可重現，但不是每次都會發生

我用和原始情境非常接近的方式，連跑 3 次 CLI：

- 同樣走 `--text` 路徑
- 同樣使用 `gemini-3.1-flash-tts-preview`
- 關閉 cache
- **不指定 speaker**，讓程式隨機選 voice

結果如下：

| Run | Voice | 長度 | 判讀 |
| --- | --- | --- | --- |
| 1 | `leda` | **40.0 秒** | 尾端仍有明顯能量，屬異常提前結束 |
| 2 | `despina` | 69.64 秒 | 近乎靜音收尾，屬自然結束 |
| 3 | `sulafat` | 69.32 秒 | 近乎靜音收尾，屬自然結束 |

這說明：

- 40 秒現象不是幻覺，**真的可以重現**
- 但它**不是固定發生**
- 它至少與 **voice / 上游回應波動 / stream 異常** 有關

### 4. `Leda` 的 direct API 結果顯示：不穩定，但不是 `MAX_TOKENS`

對 `Leda` 直接重打 Gemini API 的結果：

- `generateContent`：**67.48 秒**，`finishReason=STOP`
- 一次 `streamGenerateContent`：**70.64 秒**，`finishReason=OTHER`
- 再連續重放 8 次 `streamGenerateContent`：
  - 多數回應在 **66.8 ~ 69.8 秒**
  - 多數 `finishReason=STOP`
  - 但有 2 次 `finishReason=OTHER`
  - 最短一次只有 **60.0 秒**

這有兩個重要意義：

1. `Leda` 本身**可以**對同一份內容產出遠超過 40 秒的音訊，所以「`Leda` 固定 40 秒上限」也不成立。
2. `streamGenerateContent` 確實可能出現**異常提早結束**，而目前抓到的最強模型端訊號是 **`finishReason=OTHER`**，不是 `MAX_TOKENS`。

### 5. 目前 CLI 的行為會把上游異常包裝成「看似成功」

程式碼位置：`src/gemini-tts-cli.cs:519-700`

目前 `GeneratePcmBytes(...)` 的邏輯是：

1. 讀取 `streamGenerateContent` 回應的每個 chunk
2. 收集所有 `inlineData.data`
3. 只要有任何音訊資料，就直接把音訊拼起來回傳
4. 即使同時讀到了 `finishReason`，**也不會在「有音訊」時把它視為失敗**

因此只要上游回來的是：

- 「部分音訊」+「異常停止」

CLI 仍然會：

- 正常輸出一個合法的 WAV
- 不顯示警告
- 讓使用者以為是模型自然講完

這正是「檔案存在、指令成功、但講到一半停住」的根本原因之一。

## 目前最佳判斷

根據這次 live 證據，最佳結論如下：

1. **不是固定 40 秒硬上限**
2. **40 秒異常是真實存在的**
3. 目前最可能的原因是：
   - preview 模型或 stream 路徑的**間歇性早停**
   - 且這種異常不一定每次都會發生
4. 在這次研究中，**最接近鐵證的模型端訊號是 `finishReason=OTHER`**
5. 目前沒有證據顯示這個案例是 `MAX_TOKENS` 導致

## 建議後續修正方向

1. **在 CLI 顯示 `finishReason` / `finishMessage`**
   - 只要不是明確的自然結束，就應提示使用者

2. **對非 `STOP` 的音訊結果加上警告或失敗狀態**
   - 目前「有音訊就算成功」的策略太寬鬆

3. **對長文加入 chunk-and-merge 流程**
   - 即使這次不是固定 40 秒限制，長文仍然適合切段重試與合併

4. **針對 `streamGenerateContent` 的異常提早結束加 retry / fallback**
   - 尤其當 `finishReason != STOP` 時

## 信心評估

### 高信心

- 這份輸入**不是**因為官方 token 上限而固定卡在 40 秒
- 同一份內容可以穩定產出超過 40 秒
- CLI 的確能重現 40 秒異常檔案
- 目前 CLI 會隱藏有音訊時的異常 `finishReason`

### 中度信心

- 問題根源是 preview / stream 路徑的**間歇性上游異常**

### 尚未完全證實

- 還沒直接抓到一筆「剛好 40.0 秒」且同時帶有 `finishReason=OTHER` 的 API 原始回應
- 目前最短直接 API 異常回應是 **60.0 秒**
